# Design

## Context

One VM with Docker and Caddy, GitHub-hosted runners only, images on ghcr.io, a deploy that backs up and keeps the old version serving until the new one is confirmed, the online backup API, and a maintainer's Mac pulling the backups.

## Decisions

- **Backups inside the app**: a timer in the server process, not cron on the host, since the process already holds the database and the backup API needs it. Every hour it writes `backups/latest.db` next to the database, through a temporary file that's checked with `PRAGMA integrity_check` and then renamed, so a bad copy never replaces a good one. The first backup after 03:00 Bucharest time is also kept as `backups/norless-YYYY-MM-DD.db`, and those older than 14 days are deleted. `npm run backup` makes one by hand (the deploy uses it).
- **Pulling over SSH**: the Mac's key on the VM forces a command (`pull-backup.sh`) that writes the time to `backups/pulled-at` and streams `backups/latest.db`; the Mac's cron saves it into a synced folder. The same key copies the recordings and the slides the Mac doesn't have yet. No token over HTTP: an SSH key limited to one script exposes nothing on the web.
- **The VM**: a Hetzner CAX11 (Arm, 2 vCPU, 4 GB, 40 GB) in Nuremberg on Debian, about €7.86 a month with VAT and IPv4. Debian has no snapd or extra cloud agents, so the system idles at about 220 MB. A 2 GB swap file takes the spikes, such as a deploy's two versions of the app. CI builds the images on the VM's architecture: `setup.sh` sets the repository variable `IMAGE_RUNNER` to GitHub's Arm runner for an Arm VM. No Hetzner backups (20% more): the app's backups and the Mac's copy are enough.
- **Production only on the VM**: production takes about 0.5 GB idle (the app 174 MB, its converter 45 MB, the system, Docker and Caddy the rest); a staging app with its own converter would double the app's part and its peaks. Docker costs only 60 to 100 MB and keeps the converter sandboxed, so it stays. Each version is tried first on the Mac with `deploy/rehearse.sh <backup.db>` (the newest hourly pull): it builds the image, runs it on a copy of the backup, and checks that it starts (its migrations ran), its home page loads and the migrated database passes the integrity check.
- **Compose and Caddy**: `deploy/compose.yaml` runs `caddy`, `norless` (volume `norless-data`) and its `converter`. Caddy serves `norless.com`, and `app.norless.com` and `app-ua.norless.com`, whose requests the app redirects itself. The image tags are in `deploy/.env` on the VM.
- **A deploy key that can only deploy**: the deploy user's `authorized_keys` line forces `deploy.sh` with `command=`, and the script accepts only `production <tag>`, with a tag of letters, digits, dots and dashes.
- **The old version keeps serving**: `deploy.sh` backs up, starts the new tag as a candidate beside the running service (`docker compose run`, named `norless-candidate`, with the same settings and volume), polls its health for 60 seconds, and waits for a maintainer to confirm in GitHub (the `production-switch` environment's required reviewers). Confirmed, `deploy.sh production <tag> switch` restarts the service on the new tag; Caddy lists the candidate after the service with `lb_policy first`, so requests go to it only while the service restarts, and nobody sees the switch. A candidate that fails its check, or isn't confirmed, is dropped while the old version never stopped. While both run, the old version works on what the new one migrated, so migrations only add.
- **Deploys by hand only**: nothing deploys by itself, not even a merge to `main`, so nothing changes during a service unless a maintainer chooses to; no Sunday freeze is needed.
- **Email**: Mailgun's Free plan, one domain, `mg.norless.com` in the EU region, with SPF, DKIM and MX at Name.com, open and click tracking off. Emails go from `Norless <login@norless.com>` (DKIM aligned with norless.com) with a Reply-To the operator sets. norless.com's own mail is forwarded by Name.com, with DMARC at `p=none` and no reports.
- **Alerts**: to the app team (`APP_TEAM_EMAILS`): no good hourly backup for 3 hours, no pull for 48 hours, disk over 80%, more than 20 server errors in 10 minutes, and, from an external uptime check, the health check failing for 2 minutes. Until email works they're written to the server log.
- **Setup script**: `deploy/setup.sh`, a resumable bash wizard a maintainer runs on the Mac, walks through everything only they can do, in order: the GitHub repository (through `gh`), its secrets and the `production-switch` environment, the VM (created in Hetzner's console with a root key the script makes; then Docker, swap, the firewall and the deploy user over SSH), DNS, the VM's `.env` (Mailgun, Google OAuth, `APP_TEAM_EMAILS`, VAPID keys it generates, YouTube), the deploy key (made, installed, stored in GitHub, checked that it can only run `deploy.sh`, then deleted from the Mac), the first images made public on ghcr.io, the Mac's backup key and cron, the uptime monitor, GitHub Pages for the manual, inviting Nicolae Matei as maintainer, and the SPF record. Each step is checked, can be skipped, and is remembered in `~/.norless-setup`, outside the repo. Secrets are typed straight into the VM's `.env` or GitHub.
- **The shadow Sunday**: one laptop, one projector, two browser tabs. The new app runs the service from production, which nobody else uses before cutover, its projector window fullscreen on the projector; the old app is open in another tab with the same playlist, its output window ready, and the switch between them is rehearsed beforehand. It runs online only: its fallback is the old app's tab. The playlist is built in the old app as usual; on Saturday night production is updated in place from a fresh prod dump: songs and playlists come in fresh through the re-runnable import, while what exists only in the new app stays (invited members, logins, the paired TV, screens, instruments, preferences). Cutover night works the same way.
- **The stage TV**: a Samsung. On the shadow Sunday its browser pairs at `norless.com/pair` and shows the stage monitor (production has the stage monitor and pairing switched on besides Classic), with "Autorun Last App" on; if it misbehaves or doesn't come back after a power cycle, an HDMI cable from the operator laptop, or what it shows today.
- **The stream's lyrics**: they stay on the old app on the shadow Sunday; the new app's broadcast screen is tried at a weekday rehearsal first.
- **Cutover**: the night before the first real Sunday, a fresh dump is re-imported into production and DNS switches. The old app stays writable as the fallback until two good Sundays on the new app (a good Sunday is the operator's call), then read-only for 3 months, then app.norless.com redirects and the old server stops, its last dump kept. Nothing syncs back: from cutover the team edits only in the new app.
- **Who is invited when**: before the shadow Sunday, only the shadow crew and that Sunday's operators; everyone else at cutover, from the imported-accounts review list. The invitation suggests no role: each person's roles are picked (the form starts empty). The imported accounts that never logged in, or not in two years, are decided one by one, never deleted in bulk.
- **Features a week at a time**: the shadow Sunday and the first real Sundays run with Classic only, as the import starts; then owners switch on one or two features a week, in the order in PLAN.md (what the team asked for first), each announced by What's new.
- **Training videos**: about a minute each, recorded by Playwright scripts on a real-data import so they're taken again when the UI changes, with English captions drawn on the page at each step, a ring around what's clicked, the mouse drawn as a gliding arrow, a fingertip where a phone is tapped, and the clicks and keys heard (made from tones and noise; no voice). First only what Classic has: the operator laptop, building a playlist (from the last service's real entries, so nothing is invented), a phone controlling the slides and logging the laptop in, and the projectors; the other features get theirs the week each is switched on. The videos hold real data, so they stay out of the repo. Filming is postponed until asked again: the runs were flaky and slow, and the videos share the live room, so each picks a song the ones before didn't leave live.

## Risks / Trade-offs

- [A timer in the app stops when the app is down] → The deploy backs up before each change, the Mac's pull notices a stale copy by its date, and the 3-hour alert covers a silent stop.
- [No staging on the VM: a version is tried on the Mac, not on the server it will run on] → The image is the same build and the data the newest backup; what the Mac can't show (the VM's network, Caddy, the real converter) the candidate beside production shows before the switch is confirmed.
