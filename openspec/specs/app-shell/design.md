# App shell design

Why the app's frame (libraries, connection, offline, states, bars, theme) works as the `app-shell` spec says.

## Decisions

- **HeroUI 3 on React Aria, with Tailwind 4**: most screens are custom layouts (stage views, chord grids, timelines), which utilities suit. Themes nest (a dark stage preview in a light page, each projector with its own look), and HeroUI switches theme with `.dark` or `data-theme` on any element. Tailwind 4's container queries cover one view at many sizes. React Aria gives the same press, long-press, keyboard and drag behavior everywhere, with Romanian and Ukrainian strings; `optimize-locales-plugin` keeps only en, ro and uk. Where HeroUI has no component (sortable lists, tile buttons), React Aria is used directly.
- **wouter** for routes under `/:community`: hooks, params, nested routes and links in about 2 KB is all permalinks need. HeroUI's `Link` doesn't route, so links are wouter's `Link` with HeroUI's class.
- **Lucide icons**: about 1,600 line icons including music ones, only the used ones are bundled, and they are components, so offline use works. Icons shared by several views live in one file, so the same action has the same icon everywhere.
- **Maintained libraries over hand-written ones** for solved problems: vite-plugin-pwa (Workbox), i18next-cli, @axe-core/playwright. Small tested pieces stay hand-written (reconnect, contrast check).
- **One WebSocket, topics, HTTP for changes**: `/api/live` carries `subscribe` and events; saving or reordering is an HTTP call, so validation, roles and tests (`inject`) stay in one place. Only ephemeral, high-frequency data (a drag, a draft) may use the socket. Topics live in memory, which assumes one server process.
- **Heartbeat in messages**: a `ping` every 25 s, a `pong` back, and 60 s of silence means dead. Browsers don't expose ping frames, so a dropped Wi-Fi or a waking laptop would go unnoticed.
- **Reconnect**: retries start at 0.5 s and double to 5 s, with jitter so clients don't return together after a restart. The browser's `online` event and the page turning visible retry at once. The indicator shows after a 1 s delay, so a quick reconnect doesn't flash. Events published while disconnected are missed, so a feature refetches or answers the subscription with its state.
- **Socket safety**: `ws` directly, with the `Origin` checked on the upgrade (a socket sends the session cookie and CORS doesn't bind it); messages over 64 KiB close it, and a socket follows at most 100 topics.
- **Service worker**: vite-plugin-pwa's `generateSW` with `registerType: "prompt"`. It precaches the built files, so the installed app opens in under a second and drops older builds' files. `/api/` and paths the server answers itself (short links, old-link redirects) stay out of the navigation fallback. The manifest stays a hand-kept file.
- **New versions**: the page asks the service worker for an update at each live reconnect (a deploy restarts the server, so every open page reconnects) and hourly. Members get a one-line notice with Reload and are never reloaded, since a reload could cost unsaved text or interrupt a service. Screens and stage devices reload by themselves, but only while they show nothing (blank room, nothing live, or no service by the schedule): a TV on autorun would keep old code for weeks. Closing the notice puts it away until a later version; the waiting one still takes over on the next load.
- **Back closes what's open before it leaves the page**: each thing that opens (the phone's slides column, a dialog, drawer or menu, the in-page projector) takes one history entry through `useBackCloses` in `src/client/ui/back.ts`; back closes it, and closed another way it takes its entry back off, unless the page moved on. Overlays are found, not wired one by one: the frame watches for an open modal dialog or menu, and on back presses Esc on the focused element, so React Aria closes the topmost, as about thirty overlays already close on Esc. A dialog that ignores Esc keeps its own ✕, and back then leaves the page as it is.
- **"Press back again to close", in the installed app only**: on Android the installed app closed on back from its first page, mid-service. It puts a guard entry over its first page, and back onto it shows the message for 2 seconds. In a browser tab, holding someone on a page is hostile.
- **The manifest's `id` is `/`**: the app is the root, whatever page it was installed from. It's the one part of the app's identity the page controls; what Chrome's "Copy app link" copies isn't documented.
- **Offline cache for logged-in people and self-projecting screens only**: following along needs the network anyway, and fifty visitor phones each pulling about 1 MB mid-service strained the church's wifi. Registration happens once from React when the person turns out to be logged in or the route is a screen. A visitor's page left open across a deploy reloads when a file is gone (`vite:preloadError`), at most once a minute so a missing file can't loop.
- **Dark splash for everyone**: Android takes one color from the manifest, and a light page after a dark splash is calmer in a dark room than the reverse. Before the styles load, `index.html` sets the system's light or dark background inline, and the browser bar follows.
- **Loading shell in `index.html`**: a first load was blank for 3.6 s on slow 4G, and libraries are most of the bundle, so the page holds the app's own grey placeholder bars, shown after 300 ms. No logo or spinner. It sits beside `#root`, since React's first render would clear `#root` while the top `Suspense` (which shows nothing, for screens) still loads. `Root` removes it in a layout effect once real content commits, so the two never show together. Screen routes drop it before it can show. Its label follows `navigator.language`, since the strings haven't loaded.
- **States**: a placeholder shows only after 300 ms, so quick loads don't flash. Empty states are calm and in the theme, errors say what failed and keep typed text, so the two never look alike. `ActionButton` blocks a second run. Audience screens keep the last content and show nothing else.
- **Device type from the screen, not the user agent**: the shorter screen side under 600 px is a phone; otherwise a touch pointer is a tablet and a mouse a laptop. iPadOS reports itself as a Mac and client hints only say mobile or not. The override is kept on the device; preferences are stored with the member per device type, so a new phone gets their phone settings.
- **Layouts are a list per view**: each entry has a name, its device types, its feature and a component, so adding a layout never touches the others.
- **Page width**: live views (a playlist, Host) use the whole window; pages to read stay at most 1280 px (`max-w-7xl`), for line length.
- **Text size by CSS `zoom`** (60 to 200%) on stage layouts, so everything scales together.
- **Theme scopes**: the app, stage layouts and room screens each set the same CSS variables, so any element switches scope by attribute. The community theme fills them in every scope.
- **Community theme**: primary color (`--accent`), a light background tint, a font and a logo (a data URL up to about 200 KB). The font file (woff2 or woff, up to about 300 KB) is uploaded by an owner and served by Norless at `/api/communities/<slug>/font`, cached under a versioned address, so no font site learns who opens Norless. Fonts like Switzer can't be redistributed, so the file isn't in the repo.
- **Contrast is checked on save**: white on the primary, text on the tint, and the primary as text on the tint, each at 4.5:1 or more; the server refuses a theme that fails. A neutral like `#80756a` on `#f9f5f2` is 4.4:1, so it isn't used for text. HeroUI's defaults for white on the main color, muted text and soft success chips are darkened in `index.css`, as axe found.
- **Live color**: the primary's hue plus 180 degrees at full saturation, then OKLCH lightness 0.64. The opposite hue keeps live from reading as the selection (the primary). Full strength and one lightness keep a dark or greyish primary from going brown, and a frame of it reaches 3:1 on light and dark pages. Each theme scope derives its own.
- **Steady layout**: marks (live, selected, focused) use a border every row already has, or a fixed height, or both states stacked in one grid cell. Focus rings are inset in scrolling columns.
- **Tooltips are `Tip`**: browser `title` tooltips can't be styled or reached on touch. `Tip` shows on hover and focus, and on a touch screen after a 500 ms press, which then doesn't press the button.
- **English for everyone**: the Romanian text felt off, so the language picker is off (`languageChoice`). Romanian and Ukrainian stay complete and checked, so the picker returns by flipping one flag. Times use `hourCycle: "h23"` everywhere, the server's notification text included.
- **Language labels** are a country code with a flag the app draws, `RO` and `UA`, since Ukrainian's `uk` reads as the United Kingdom, and Windows shows flag emoji as letters. English keeps `EN` with the United Kingdom's flag, so the three labels look alike.
- **Checks in `npm run check`**: `i18next-cli lint` fails on text outside `t()`. `locales.test.ts` stays, since it compares placeholders, and `extract` isn't used because it rewrites the JSON layout. The e2e `test` fixture runs axe on every page a test left open and on every other page its context visited, in light and dark, with transitions off so colors are measured as they end, and fails on serious and critical violations. React Aria's hidden live announcer is excluded.
- **Short codes**: 6 characters from letters that can't be mistaken for each other and digits, always with a digit (7 after 20 collisions), so they never match a word route such as `/pair`; community slugs have none. Kept in `short_codes` for good, so a code is never reused. A screen's code points to its secret, so a new secret retires it. Typing it on a TV is easy; someone who guesses one sees what the projector page already shows publicly.
- **Privacy**: the community is the responsible party, from its settings. The operator and services come from the server's `OPERATOR` and `PRIVACY_SERVICES`. The only cookie is the session, so no banner.
- **Menus, no footer**: About, Privacy and Install live in the menus, since a footer makes a laptop app feel like a website, and on a phone they showed first while the page loaded.
- **One community bar**: logo and name, Playlists, then Stage, Team and More menus (a one-page menu shows as that link, an empty one hides), then language and account. Stacking the title, links, who is online, layout, problems and search pushed entries halfway down a laptop. Items navigate in-app. The Norless name shows only outside communities.
- **Phone bar**: the same everywhere, burger left and photo right (name in a tooltip), so there is one layout to learn.
- **The playlist's title is in the bar**: renaming is rare, so it isn't a big field on the page. The page fills a slot in the bar through a portal (`BarPlace`), so bars know nothing of playlists. Long titles cut with an ellipsis, the community's name first, so the photo stays. Problems, the end estimate and who is online stay in the page's row; in the bar they pushed the title and photo out on a phone.
- **Phone title is the menu**: tapping it opens the playlist's actions, Rename first, with a small ▾ and no ⋯; a person with no action sees plain text. Laptops keep click-to-rename and ⋯. The community's name takes its own centered line above the bar, chosen by the address, so it is there before the playlist loads and nothing moves.
- **Destructive row actions** go in the row's ⋯ menu with a confirmation (`RowMenu`), where a slip doesn't hit them.
- **The start page is the app at `norless.com/`**: one origin and one deploy, so nothing changes for DNS, the Google login origin, installed apps, short links or QR codes, and the page can tell a known device and send it on. The address had to be settled before cutover, after which installed apps and printed QR codes pin it.
- **It's for the team first, then curious visitors**: no pricing, sign-up or self-hosting. About and the source stay in the ⋯ menu, as on every page, with no footer. A card with the app's icon holds one line on what Norless is, Install as the main button and the way into the community; Log in is only in the header, which already has it.
- **Install first, log in inside the installed app**: on an iPhone the installed app keeps its own storage, so logging in in Safari first could mean logging in twice. The installed app opens the community, where Log in is.
- **A fresh device is one with no last community, in a browser tab**: the installed app never shows the presentation, since its storage may be empty on its first launch even when the browser's isn't. A member who cleared the browser's storage sees it once, and the community's button gets them back in.
- **With several communities, the list**: a fresh visit can't say which community is wanted, and the community's address is the way in.
- **Following along from the start page** uses the same follow view as the community's home, for the one community, only while its follow-along switch is on.
- **The manual is a link, with no screenshots on the page**: the manual's pictures on GitHub Pages would send every fresh visitor's address to GitHub before they chose anything. Following the link is the visitor's choice. Its address comes from the running version's source address (About's), whose GitHub Pages site is the manual, so no account name is in the code, and a server without a GitHub source shows no manual link.
- **The window's title is the place, then the community** ("Playlists · Unu-Unu"): short enough for a window's title bar, and the app's icon already says Norless.
- **Menu items that open a page are links**: React Aria renders an item with `href` as a link, so the browser's own gestures work (a new tab, copying the address), and the router opens it.
- **Who's online stacks under the photo on a phone**: the others' photos sit under one's own, so the row above the search box goes and nobody sees themselves twice. The photo opens the account menu as a full page, who's online at its top, each with their device and view.

## Rejected

- Mantine: one color scheme for the whole page, so nested themes and container queries would be hand-written everywhere.
- React Router (large, mostly framework features), TanStack Router (more setup), and our own History code.
- Tabler, Gravity UI and Iconify icons: Gravity has few music icons, and Iconify loads icons over the network, which offline use can't.
- Flag emoji for languages.
- A hand-written service worker: it never removed old builds' files.
- A new-version notice on screens, or reloading every page at once.
- A back handler in each dialog: every file that opens one would change.
- Showing `/` in the address bar while Chrome's install prompt is open: a guess, with a visible flicker.
- A spinner or logo as the first-load screen, and trimming the bundle further as the only fix: libraries are most of it.
- A fixed orange live color: it sat beside a terracotta selection.
- A choice of splash color by system mode: the manifest takes one.
- The app on `app.norless.com` with a static page on `norless.com`: redirect rules for short links and community addresses, a new Google origin, and a page that can't tell a member's device. Or with the presentation and manual as one GitHub Pages site: Pages can't redirect, so short links and community addresses would move to the longer host.
- Guessing a fresh visitor's community from their IP address or location: a privacy cost for an unreliable answer.
- The community's name between the playlist's ⋯ and the photo (cut to "Exam…"), a label under the bar, or only inside the burger.
- Axe failing on any violation (noise on custom stage layouts) or only reporting.
- Lint warnings only for hard-coded text: they pile up.
- "· Norless" at the end of the window's title, or the place alone.
- One menu for both the account and who's online, or hiding who's online on phones.
