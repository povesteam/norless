# Operations design

Why Norless runs the way the spec says: one small server, deploys that can't break a service, and the files people send read in a place that can't reach the data.

## Decisions

- **One VM with Docker Compose and Caddy**: a Hetzner CX23 (x86) or CAX11 (Arm) with 2 vCPU, 4 GB and 40 GB, in Germany or Finland, whichever is in stock. The data is one SQLite file and one Node process, so one server is enough and nothing needs replicating. Debian idles at about 220 MB, a 2 GB swap file takes the spikes (a deploy runs two versions of the app for a minute), and the firewall lets in only SSH, HTTP and HTTPS. SSH takes keys only, since bots try passwords on port 22 all day. Caddy gets the HTTPS certificates itself.
- **No Hetzner backups**: the app's hourly backups and the copy pulled off the server cover the data, and Hetzner's would add 20% to the price.
- **Backups leave the server by being pulled**: a maintainer's Mac tries every hour it's awake and, at the day's first try, fetches the latest backup over SSH with a key whose forced `command=` can run only `pull-backup.sh`. One copy a day is enough there, since the server keeps 14 daily copies itself, and a day's copy is never overwritten. The same key fetches recordings and slides, which aren't in the database. A key that can do one thing is worth little if stolen. A sleeping Mac would fail silently, so the server alerts when no pull has happened for a while.
- **Alerts by email to the app team**: no good backup, no pull, the disk over 80% full, a burst of server errors. Each is also written to the log, so they show before email works, and is sent again once a day while it lasts. Whether the server answers at all is checked from outside by an uptime monitor on `/api/health`, which also fails when the database doesn't answer, because a server that is down can't report itself.
- **CI runs on GitHub-hosted runners only**: free for public repos, and no self-hosted runner on the VM, since a pull request from a fork could run arbitrary code on the server. The VM is only the deploy target. `pull_request_target` is never used on fork pull requests, and AI review, where used, runs only for maintainers' pull requests or when a maintainer asks, because a malicious pull request could instruct it or leak secrets.
- **Checks before merge**: lint, format, typecheck, the specs' validation, unit tests, Playwright against a temporary database (split across four runners, each with its own server, so CI takes minutes less: Chromium's tests in three shards, and the live and Classic rooms, which run one test at a time, in the fourth), and a Docker build of both images that is then started and health-checked as production runs it. Imports missing from `dependencies` only fail there, since development has every dependency. Every commit must carry a DCO sign-off.
- **Supply chain**: actions are pinned to commit SHAs, Dependabot waits 3 days before proposing a version, npm installs only versions at least 2 days old with exact versions saved, and install scripts are denied unless listed. GitHub's own scanning (secret scanning with push protection, dependency review for licenses that don't fit AGPL) is preferred to extra services.
- **Deploys by hand only**: a maintainer runs the Deploy workflow, never a merge, so nothing changes during a service unless someone chooses it, and no freeze is needed. The workflow runs CI (skipped when it already passed on the commit pushed to main, rather than spending its minutes again), builds both images for the VM's architecture, pushes them to ghcr.io (public, so the VM pulls without logging in), and connects over SSH as a deploy user whose key can run only `deploy.sh`. The script accepts only `production <tag>`, with a tag of letters, digits, dots and dashes.
- **The old version keeps serving**: `deploy.sh` backs up, updates the converter, starts the new image beside the running one as a candidate and waits up to a minute for its health. A maintainer then confirms in GitHub (an environment with required reviewers). The service restarts on the new tag while Caddy sends requests to the candidate, listed second with `lb_policy first`, only while the service doesn't answer, so nobody sees the switch. A candidate that isn't healthy or isn't confirmed is stopped, and the old version never stopped. While both run, the old one works on a database the new one may have migrated, so migrations only add, and a following release drops what is no longer used.
- **Staging isn't on the VM**: a second app with a second converter doubled the app's memory and its peaks. A version is tried on real data on a maintainer's Mac first (`deploy/rehearse.sh <backup.db>`): it builds the image, runs it on a copy of the newest pulled backup, and checks that it starts (its migrations ran), its home page loads and the database passes the integrity check.
- **Files read apart from the data**: ffmpeg and poppler read recordings, pictures and PDFs from people and from the internet, and each has had security holes. A bad file read in the container that holds the database could reach it, and a heavy conversion competes with the app for memory during a service. So they run in a container of their own, built from this repo.
- **Bytes in, results out**: a job's file is the request body and its options are in the query. A picture comes back as the JPEG itself and a recording's files as `multipart/form-data`, read with `Response.formData()`, so no library. The converter writes only to its own `/tmp` and keeps nothing, and the data folder and backups don't change.
- **A converter without a build**: `node:http` and `node:child_process`, run by Node 24 directly (type stripping), with no dependencies. ffmpeg opens pictures through a named reader (`jpeg_pipe`, `png_pipe`, and so on), so it opens nothing else.
- **One container, a queue per kind of job**: documents and recordings one at a time, pictures two. A job waiting longer than its limit is refused with 503 and the app tries again. Recordings run under `nice`. The `/v1/…` paths stay stable, so an app and a converter one version apart work together, which a deploy relies on.
- **Limits that protect the app**: one of the two CPUs and 1.5 GB (`cpus`, `mem_limit`), a read-only root, `/tmp` as a 1 GB tmpfs (a 4-hour recording is about 230 MB and its parts must fit with it), the `node` user, and an internal Docker network that only the app joins, so the converter has no route to the internet.
- **A converter that's away doesn't stop the app**: slide entries stay "Preparing" and are tried every minute, a recording's cut every 5 minutes, and avatar and link-preview pictures are skipped and taken next time. An avatar upload is refused with "try again soon". The converter's health isn't part of the app's, since its problem mustn't roll back an app deploy. The app checks it every minute and tells the app team once after 5 minutes away, and once when it's back.
- **Converter first in a deploy**: it starts with the new tag and must be healthy within a minute, or the old one comes back and the deploy stops. It isn't put back when the app's candidate fails, since its jobs keep their paths.
- **The converter runs everywhere**: development and tests start the same container (`npm run converter`, `CONVERTER_URL`), and its own tests run against it in the e2e run and CI. `npm run check` stays fast and without Docker, with a small stub server answering for it.
- **A small app image**: `node:24-alpine`, 8 MB of base against Debian's 108. After `npm ci --omit=dev`, npm, corepack and yarn go, and so do `better-sqlite3`'s SQLite sources and the builds for other platforms; both musl builds stay (x64 for the VM, arm64 for a Mac). A shell stays because `pull-backup.sh` runs `sh`, `find`, `sort`, `comm` and `tar` inside the container. The build stage stays on Debian, since it only makes JavaScript.
- **An Alpine converter**: its ffmpeg is a quarter the size of Debian's, which pulls in X11 and Vulkan. Liberation fonts (metric-compatible with Arial and Times New Roman) and DejaVu stay for PDFs that don't embed theirs.
- **PDFs and pictures only, drawn with `pdftoppm`**: PowerPoint, Keynote, Google Slides and Canva each export a PDF that looks as designed. A dropped presentation adds nothing and says where each app exports a PDF.

## Rejected

- A self-hosted CI runner on the VM: a fork's pull request could run code there.
- Automatic deploys, even on a merge to `main`: a change during a service.
- Rolling back after the new version already served, or leaving the site down for a person to decide: the old version keeps serving until the new one is confirmed.
- A backup download over HTTP with a token: a key limited to one script can't do anything else.
- A staging environment on the VM: it doubled the memory production needs.
- Kamal: it would replace Caddy, and `deploy.sh` already switches versions.
- Healthchecks.io: the app's own alerts cover it.
- LibreOffice for presentations: it lost fonts, animations and videos, took several hundred MB of memory per file, and made the converter's image 1.3 GB (437 MB without it). No small, stable converter for presentation files exists.
- pdf.js in the browser: each device would draw every page, where the server draws each once and caches it.
- LibreOffice or ffmpeg in the app's image: one bad file read next to the database could reach it.
- A container per tool: one with a queue per kind of job is enough.
- A shared volume between the app and the converter: less copying, but it would hand the converter every file.
- A distroless app image: `pull-backup.sh` needs a shell in it.
