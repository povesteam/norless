# Screens design

Why screens work as the spec says: the mechanisms, numbers and trade-offs behind the output views.

## Decisions

- **Secret URL, no login**: a screen's URL holds a random secret (18 random bytes, base64url) and shows only what is live, which is public anyway. A TV or a projector laptop shouldn't need a login; a leaked link is revoked by regenerating the secret.
- **Quick projector without a screen record**: `/<community>/projector/<language>` shows the live content in one language with no setup, and keeps working next to real screens.
- **Pairing by token**: the device keeps a random token in browser storage. The server hands out a six-digit code, held in memory for 5 minutes; the device asks for a new one every 4.5 minutes by its own clock, and after a server restart. A paired device opens its screen with its token, as a secret URL does, so regenerating the screen's secret doesn't unpair it. Pairing it again moves it. Pending codes are capped at 1000 so a flood can't grow the memory.
- **QR for pairing**: the QR code (lean-qr: small, no dependencies) holds `<origin>/pair/<code>`. A phone's camera opens it and the team member lands on the pairing dialog with the code filled in, after logging in if needed.
- **Fit by measuring**: the browser finds the largest font that fits by bisection between 6 and 600 px, measuring the rendered slide to half a pixel, and again on every resize. Song lines never wrap, so the font shrinks and a line stays whole; Bible text wraps.
- **Too-small warning is estimated on the server**: the server can't measure a screen, so it estimates the largest font at which a slide fits a 16:9 projector, from the line count and the widest line. A character's width depends on its kind: narrow letters and spaces 0.22 of the font size, m and w 0.75, capitals 0.6, the rest 0.58. "Too small" is under 70% of a four-line slide of 32-character lines. The constants were fitted to the sizes projectors really gave 730 real slides: every slide under 70% is found, and 14 of 708 others are wrongly warned about.
- **Title-safe margins of 5% per side**: 5% of the width and 5% of the height, the graphics-safe area broadcast uses for 16:9. TVs crop the picture's edges, and the stage monitor runs on a TV. It applies to the projector, the stage monitor, and the musicians and vocalists screens, previews included, scaled. At 1280 x 720 the text box is 1152 x 648, so a projector that doesn't crop shows text up to about 7% smaller. Slides from files and start or end pages fill the screen as designed; the overlay has its own margins.
- **Overlay as a lower third**: the live state moves by slides, so the overlay can't page through a slide two lines at a time. It shows the whole slide in at most two rows: three or four lines join in pairs with " / ", longer slides shrink. It sits in a box 22% high, 10% in from the sides and 8% above the bottom. Transparent is the default, for OBS. Text gets an outline and a shadow so it reads over any video.
- **Dark before any code runs**: a script in the head of `index.html`, before any stylesheet, sets the page and the browser bar black on screen pages (`/s/…`, `/pair`, projector, local projection, stage) and on the musicians and vocalists views, whatever the system's mode. A reload on a laptop in light mode must not flash white on a projector or in a dark room. A reader who chose light sees black for a moment, which beats white in a dark room.
- **A paired screen loads in its last background**: the device remembers it in browser storage (an overlay's transparent, green or black; a projector's or stage monitor's own color; black for the rest; black the first time). Otherwise a transparent overlay would flash black in the stream while it loads.
- **Browser bars follow the view**: phones take the view's color for `theme-color` on the stage monitor, musicians, vocalists, screens and the pairing page. A transparent overlay leaves them alone. Chrome can't color Android's navigation bar in a tab, so Full screen hides it.
- **Fullscreen button and pointer**: the button shows for 3 seconds after opening and after any touch or pointer move; the pointer hides after 3 seconds still. The button is an icon with its name in a tooltip and isn't offered where the browser can't (iPhone).
- **Displays only after one explicit grant**: displays are listed through the Window Management API only when the permission is already granted. Only "Choose displays" asks, so nobody gets a prompt they didn't ask for; until then screens open in a new window. Without a choice, a screen uses the display chosen before for it on this device (browser storage), else the first that isn't the laptop's own.
- **Local projection stays in one browser**: a tab keeps its own live state and sends it to the projector window it opened through a BroadcastChannel. No server, no login, and the room's live state is never touched.
- **Parts are whole**: musicians, vocalists and the stage monitor show each part as one block, never a half. Most slides have no name, so an unnamed slide is its own part, numbered among the verses; a refrain named `R` returns between them in the song's order.
- **Live and next never look alike**: the live part has a frame in the live color, the next part a dashed neutral one, in dark and in light.
- **Songs without chords still show something**: most songs have none, so the musicians view shows the lyrics, key and structure and invites members who may add chords to do so.
- **Bar grid is measured**: the grid measures its width and the widest bar, before the first paint so nothing jumps. All bars go on one line when they fit; else one row per chord line (a phrase) when the longest fits; else the fewest equal rows (2 to 4) whose columns fit; past 4 rows, as many columns as fit. Every column has the same width, so bars align from row to row. Phrase rows read like the song: a verse on a phone went from 7 rows of 3, cut anywhere, to 5 rows of 4. On a phone the part's name goes above its bars to give them the width.
- **Beats share a bar**: each chord is as wide as its beats (flex-grow), equal until set. Beats per bar come from the time signature's top number, 4 without one; a bar with more chords than beats splits equally. Chords over words keep their place along the line.
- **Portrait stage views**: on a screen taller than wide, the next part goes under the live part with the same 2 : 1 share, so a phone held upright doesn't squeeze both into small text. The vocalists Sideways layout does the same when turned upright.
- **Wrap, never cut**: vocalists lines wrap at the width. A tap that starts a scroll doesn't send a part live.
- **The message moves the song**: on the stage views the message takes its own line above the song and pushes it down, since covering the title, key and time hid what the musician needs. It lives in the live state, so every stage device shows the same one until a controller clears it. Projectors and the overlay never show it.
- **Controls in one icon row on every device**: the stage views are about the song and need the room; one look everywhere is less to learn. Each icon has its name in a tooltip (`Tip`: hover, focus, and a half-second long-press that doesn't press the button and goes away after 2 seconds). A button that is running says so in words ("Stop 0:42", "72 bpm"), since that is information, not a label.
- **Input choice in a dialog**: Record and Listen for tempo open a dialog with the input chosen last, its live level, and Start, so the musician sees that the mixer feed is the one that hears the band before starting. The layouts' icon opens their menu.
- **Look ahead is private**: Earlier song and Later song step through the live playlist's songs only (dividers, texts and passages skipped) on the member's own device. A bar of fixed height says which song is shown, so parts never move. The song looked at shows with nothing live and the first part marked next, and its parts don't go live. The view goes back to live by itself when the live song changes. Screens follow the room and never offer it.
- **Slides are pictures**: the server renders each page once, at 320, 1280 and 3840 px wide. Views use `srcset`, so a 4K projector loads the 3840 one, a phone the 1280 one and a thumbnail the 320 one. The page is letterboxed on the screen's background color; the background picture and text styles don't apply. A screen with two languages shows its first language's file once, full frame, since a page is designed whole.
- **Bible references show only the reference**: Norless holds no Bible text; verses come from the bible.com extension (`bible-com-projection`).
- **Text slides use a small Markdown subset**: headings, paragraphs, bold, italic and lists, built in, with no dependency.
- **Stage monitor on any device**: `/<community>/stage` opens one in the community's languages on a TV's browser or a phone, apart from the screens with secrets.
- **Reconnect and catch up**: a screen keeps its last content while offline. The server sends the current state when a client subscribes, so a reconnected screen catches up within a second.

## Rejected

- Margin of 3% of the shorter side on every edge: under 2% of the width on 16:9, so text ran to about 20 px from the edges and a TV that crops lost lines.
- A margin setting per screen: one margin works on any display; a setting can follow if some projector's text turns out too small.
- Estimating the font by character count: it warned about 42 slides that weren't too small and missed 7 that were.
- The message as a banner over the parts: it covered the song's title and key.
- Icon buttons with an arrow beside them (Record, Listen for tempo, layouts): the top bar looked glitchy; the icon opens its dialog or menu itself.
- A list of songs to pick from in Look ahead: on a phone it would cover the parts.
- Look ahead on screens: they follow the room.
- Paging a slide two lines at a time on the overlay: the live state has no unit smaller than a slide.
- Bible verse text inside Norless's own projector: left to the bible.com extension.
