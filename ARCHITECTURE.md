# Architecture

Where things live and the patterns to copy, so a change starts from here instead of a search. Behavior is in `openspec/specs/`, plans in `PLAN.md`, rules in `AGENTS.md`. A change that adds or moves a pattern updates this file.

## Domain

- **Community**: the tenant (a church), with its languages (an open list: `ro`, `uk`, `en`), members with roles (owner, editor, team; a member may have none) and its feature switches.
- **Room**: where a presentation runs, with one live state: the main room, and temporary practice rooms beside it.
- **Song**: one song with a version per language (title and lyrics) and one music track shared by its languages (key, time signature, chords, notation, tempo).
- **Playlist**: an ordered list of entries (songs, Bible passages, dividers, text slides, slides from files), usually a service's.
- **Live state**: per room, the current entry and slide, blank or not, the mode (service or rehearsal), and who changed it last.
- **Play**: a song projected in a room, with its mode; statistics count service plays.
- **Screen**: a named output of a room (projector, stage monitor, broadcast overlay) with its languages, layout and look, following the room's live state.

## Layout

- `src/server`: Fastify app. `app.ts` wires every feature through an `attachX(app, …)` function, one file per feature, each with its `*.test.ts` next to it, in a folder per area: `auth/`, `songs/`, `playlists/`, `live/`, `schedule/`, `community/` (feedback, feature requests, privacy), `ops/` (usage, alerts, backups), with `db/`, `import/` and `cli/`; what every area uses (`app.ts`, `ids.ts`, `mail.ts`, `changes.ts`) stays at the top.
- `src/client`: React app, a folder per area: `app/` (`Root.tsx` holds the providers and the screens' routes, `App.tsx` the app's frame and its pages' routes, with wouter; the menu, About, What's new, the Features page), `ui/` (shared pieces: states, comboboxes, tooltips, icons), `data/` (fetching, live changes, the community, me, the device), `account/`, `settings/`, `songs/`, `chords/`, `playlists/`, `live/` (Classic, the controller, the live bar), `stage/` (musicians, vocalists, the stage monitor, instruments), `screens/` (projector, overlay, follow-along) and `team/`; one file per page or view.
- `src/shared`: code both sides run: song parsing and rendering (`song-text.ts`, `song-render.ts`), chords, keys and notation in `music/` (`chords.ts`, `music.ts`, `chord-track.ts`), live types (`live.ts`), feature switches (`features.ts`), preferences, screens, usage feature names.
- `src/converter`: the converter, a container of its own that reads the files from people and the internet (on Alpine: ffmpeg, and pdftoppm with slides from files): `server.ts`, plain `node:http`, run by Node as it is, one handler per job under `/v1/…` with its queue and limits in `kinds`. A new job: a handler in `jobs`, its kind, its tool in the Dockerfile, a call in `src/server/converter.ts`, a test in `e2e/converter.spec.ts`.
- `migrations/`: numbered plain SQL files, a file per area, applied in order on start; a new migration adds a file.
- `e2e/`: Playwright flows (the musicians' in `e2e/music/`), in `e2e/screenshots/` the script that takes the manual's screenshots into `screenshots/` (pictures only), and in `e2e/videos/` the team's training videos; `manual/`: the help site.

## Server

- **Database:** `src/server/db/db.ts` opens SQLite (WAL, foreign keys on) and runs `migrate()`: each new `migrations/NNN-name.sql` in its own transaction, recorded in `schema_migrations`, with foreign keys off while it runs and checked before it commits, so a migration can rebuild any table. The schema holds no CHECK constraints: rules live in code (`database` spec). Queries are `db.prepare(…)` in the feature files; no ORM.
- **Ids:** `newId()` in `src/server/ids.ts` (12 letters and digits); `idFrom(…)` gives stable ids to imported records.
- **Auth:** Google logs in two ways in `google.ts`: the redirect (openid-client) and, on the login page, Sign in with Google's ID token checked with jose and a nonce; both end in `loginWithEmail`. `attachSessions` puts the user on each request from the session cookie; `requireRole(…)` in `auth.ts` guards routes by role. Who may do what: the matrix in `openspec/specs/members/spec.md`.
- **Validation:** Fastify's JSON Schema on each route (`schema:` with `enum:` lists). Allowed values live in TypeScript (`src/shared/*.ts` or the feature file).
- **Live updates:** `src/server/live/live.ts` is a WebSocket pub/sub. A feature publishes to a topic (`live:<slug>`, `presence:<slug>`, `playlist:<id>`, `device-logins:<slug>`, …) and sends the current state when a client subscribes. Some topics carry the data, some only say "changed" and the client refetches. The change log's triggers also announce every changed table on `changes:<slug>` (`attachChanges` in `changes.ts`).
- **Live state:** `live-state.ts` keeps each community's state in memory and in `rooms.live`. `POST /api/communities/:slug/live` takes an action (go, next, previous, blank, message, page), `act()` in `live-act.ts` computes the next state, `save()` stores it and `publish()` pushes it, as the `LiveView` of `live-view.ts`. Entry changes are logged in `live_log` and `plays`, and every slide in `slide_log` (`live-log.ts`).
- **History:** `startChangeLog()` in `changes.ts` creates temporary triggers when the server starts, which log every write to the community's records in `changes` (who, when, the row, the changed fields); `runAs(userId, …)` sets who, and each request runs as its user. Song saves also keep a whole-song snapshot in `song_revisions` (`keepRevision()` in `song-saves.ts`), for History and restore. Records keep `created_by`, `updated_by`, `deleted_at` (soft delete).
- **Converter:** `src/server/converter.ts` sends a job's bytes to `CONVERTER_URL` and gets the results (`shrink`, `cutRecording`); it throws `ConverterAway` while the converter is down or busy, and callers wait and try again (a recording stays `processing`, retried every 5 minutes by `recordings.ts`) or skip (a picture); `watchConverter` alerts the app team. Unit tests answer with `stubConverter()` from `test-helpers.ts`.
- **Pictures:** `fetchPublic()` in `link-preview.ts` opens only public `https` addresses; `shrink()` makes a JPEG through the converter (or a square, for avatars); pictures live in `images` and are served at `/api/images/:id`, so browsers never contact other sites. Avatars (`avatars.ts`) are `users.avatar`.
- **Slides from files:** `src/server/playlists/slide-files.ts` takes multipart uploads (only its routes parse them), keeps each file under the data folder's `slides/<file id>/` and has the converter draw its pages in steps (`documents` in `converter.ts`: a PDF's page count, 20 pages at a time at 3840, 1280 and 320 wide), saying how far it is on `playlist:<id>`; pages are served at `/api/slide-pages/:file/:page/:width`, kept for a year. An entry's `slides` lists its files (`src/shared/slides.ts`: `fileFor` picks a screen's); a page is a slide (`pagesOf` in `shared/live.ts`), and the timer is the live state's `timer`, moved by `live-state.ts`'s ticker.
- **Mail:** `mail.ts` (Mailgun over `fetch`); without a key, development prints links.
- **Import:** `src/server/import/` reads a mongodump archive (`archive.ts`), maps it (`transform.ts`, which maps the community and plays and calls `map-people.ts`, `map-songs.ts` and `map-playlists.ts`, with what they share in `mapping.ts`; `song-matches.ts`) and writes it (`write.ts`); run with `npm run import`.

## Client

- **Bar places:** a page puts something in the top bar with `<InBar place="title">` (`app/BarPlace.tsx`, a portal), and each bar renders `<BarPlace place="title" />`, so the bars know no pages; the playlist page puts its title and ⋯ there (`PlaylistTitle.tsx`). The community's name after it takes `besideTitle`.
- **Code splitting:** screens are `lazy` in `Root.tsx` and the frame's pages in `app/pages.ts`, and the frame (`App`) loads only where it shows, so a phone following along or a stage TV loads a fraction of the app; `e2e/follow.spec.ts` keeps the follow page under 800 kB of script. A small piece that other views need (a hook, a helper, a box) lives in its own file (`parts.tsx`, `windows.ts`, `choice.tsx`; what the frame shows of a lazy page: `RequestCount.tsx`, `NearbyLogins.tsx`, `FeedbackDialog.tsx`, `NewPlaylist.tsx`, `QrImage.tsx`, `HostIcon` in `icons.tsx`), because importing it from a page would pull the whole page in. Only English strings are in the bundle; `loadLanguage` in `i18n.ts` loads the others.
- **Data:** `useJson(url, version)` in `fetch.ts` loads JSON and reports `failed` with `retry`; bump `version` to refetch. `send(method, url, body)` writes. `useChanges(slug, ...tables)` in `changes.ts` gives a version that goes up when those tables change in the community (and when the connection comes back): every view that shows data passes it.
- **bible.com:** `BibleCom.tsx` sends what's live to Nicolae's extension's windows and listens on a connection to it for verses, which go live as the state's `verse` (over what's live until Next, an entry or blank).
- **Service worker:** `ServiceWorker` in `update.ts` installs it (the offline app shell and the new-version notice) only for logged-in people and on screens' routes, so visitors' phones don't download the whole app; a page without it reloads when a deploy removed a file it needs.
- **Replays:** `replays.ts` keeps the services' streams (`streams`), found every hour on the community's channel with `findStream` from `chapters.ts`; `replayAt(at)` is the link to the second of the stream running then, which the song page, a past playlist's entries and the statistics show.
- **Big screen:** `live/BigScreen.tsx` draws each screen and each member's stage device with the views' own components at their size (1920 × 1080, or the device type's), scaled into a tile by `Scaled` (a CSS transform, which also holds what's `fixed` inside; `inert`, so a preview can't change live): no iframes and no extra connections. A musicians or vocalists view reports what it shows with `useReportStageView` (`stage/report.ts`) to presence, which lists it under its person's `views`. The width rules are in `big-screen.ts`; screens whose sizes are in container units (`cqmin`) look the same small.
- **Slides on screens:** `SlidePage` (`screens/SlidePage.tsx`) draws a slides entry's page in a screen's language with `srcset`, so each device loads the size it needs; `PageThumbs` (`live/PageThumbs.tsx`) shows the pages where a song's parts show; `playlists/SlideFiles.tsx` has the upload, the row's chips and the entry's actions.
- **Offline:** `offline-store.ts` keeps `/api/communities/:slug/offline` (songs and the newest playlists, and their slides' 4K pages, which `public/push-sw.js` answers with offline) in Cache Storage for a device whose switch is on; `Offline.tsx` has the keeper, the switch and `/<community>/offline`, which projects kept songs through local projection.
- **Live:** `createLive` in `live.ts` is the WebSocket client (reconnects); `useLiveView(slug)` in `room.ts` follows the live state, `sendLive(slug, action)` changes it; the device shows its own move at once as a guess (`guess.ts`) until the room confirms it, and Next and Previous carry the slide they start from. Local projection (no login) goes through a BroadcastChannel in `room.ts`.
- **Community bar:** `CommunityNav` in `app/CommunityNav.tsx`; `useBarGroups()` lists the pages under Stage, Team and More, each with the check that shows it, so a new page goes there.
- **Back:** `useBackCloses(open, close)` in `ui/back.ts` gives something open (the phone's slides, the phone's menu, the search) a history entry, which the system back takes off and closes it; `BackClosesOverlays` does the same for every React Aria dialog, drawer and menu by pressing Esc in it, and `BackToClose` (`app/`) asks once before the installed app closes from its first page.
- **Who and where:** `useMe()` and `useRoles(slug)` in `me.tsx`; `useCommunity()` in `community.tsx`; `useDeviceType()` and `useLayout(…)` in `device.tsx` (named layouts per device type, with `LayoutPicker`).
- **Chord track:** a song is its words (`song_versions.lyrics`) and its chord track (`songs.music`, one for every language, `src/shared/music/chord-track.ts`), nothing else. The text the views parse is built from both when a song is sent (`textOf` in `songs.ts`, `mergeText`) and never stored. Texts in the old format (chords on lines above the words) are taken apart once: the import and the seeds write them into `lyrics`, then `convertSongs` splits them. Editors edit `lyrics`, the Chords mode and key changes save the track.
- **Who leads a song:** a playlist stores the service it plans (`freeService` in `playlists.ts`); `leadsOf` reads its leading and vocal slots, `leaderOf` an entry's choice or the lead, which plays keep.
- **Notifications:** `tell` in `src/server/schedule/team-notifications.ts` writes a `notifications` row (shown in the app) and pushes it with web-push when the server has VAPID keys; `about` makes each go once. The service worker imports `public/push-sw.js`.
- **Feature switches:** every feature has a key in `features` (`src/shared/features.ts`) with the feature it needs; Classic's are always on, the rest on only when an owner switched them on (`communities.switches`). `switchesOn` turns what owners set into the features on, and views check them with `useShows()` or `<Shown>` from `community.tsx`. The Features page is `FeatureTree.tsx`, laid out by `tree-layout.ts`: d3-hierarchy's tidy tree for each feature others need (left to right, so no two lines cross), the features on their own in a grid beside them, positions computed so the lines need no measuring; a new feature takes a branch (its color) in `branchOf`.
- **Playlist edits:** `usePlaylistEdits` (`playlist-edits.tsx`) shows each change at once and sends it; `add(entry)` takes `after` (an entry's id, null for the top), which the add endpoint takes too, so an entry lands in place in one request. The search box's empty list offers `actions`, and its `place` says where the next pick goes.
- **Search box:** `SearchBox.tsx` serves the playlist's and the home page's search. While open it takes over the screen: one panel fixed over the page, down to the live bar (`[data-bottom-bar]`) or a phone's keyboard (`useFreeArea`); its results are an inline list in React Aria's popover slot (`ResultsPanel`), so they stay shown to screen readers and get no context from the box. Wide windows show the highlighted song's words (`SearchPreview.tsx`, lazy). On the server, `search.ts` asks the full-text index (`songs_fts`), then `fuzzy.ts` fills the rest with words joined and typos, from texts it keeps reduced in memory and drops in `indexSongs`.
- **Playlist names:** a playlist's title is optional; the server sends its `date` (its service's day, else the day it was made), `PlaylistName` shows the title then the date muted, `playlistName` in `src/shared/playlist-name.ts` the same as plain text (exports, notifications, the change log through `playlistNameOf`).
- **People:** `PersonAvatar` and `NameAvatar` in `NameAvatar.tsx` show a person's photo, else initials.
- **States:** `Empty`, `Placeholder`, `ErrorNotice`, `usePending`, `ActionButton` in `states.tsx`. While the app's code loads, `index.html` shows the same bars (`#shell`, after 300 ms, not on screens), and its stylesheet doesn't hold them back (the `stylesheet-after-shell` plugin in `vite.config.ts`; `main.tsx` renders once it's applied); `Root` takes them away when the first page commits (`removeShell`).
- **UI:** HeroUI 3 and Tailwind 4; theme colors are CSS variables per community (`ThemeStyle`). Shared icons in `icons.tsx`, comboboxes in `combobox.tsx`, icon-only buttons' tooltips (also on long-press) in `tip.tsx`, strings in `src/client/locales/{en,ro,uk}`.

## Tests

- **Unit:** Vitest, files next to the code. `npm test`, or one file: `npx vitest run src/server/songs/songs.test.ts`.
- **End to end:** `npm run e2e` starts a converter's container of its own on 3901 (`npm run converter`, so Docker must run; removed after the run), builds, seeds a temporary database (`e2e/seed.ts`) and serves on port 3100; one file: `npx playwright test e2e/live/stage.spec.ts`; one test: add `-g "name"`. The tests that change Unu-Unu's live room are in `e2e/live/`, a project of their own that runs one test at a time, with `servicePlaylist` and `rows` in `e2e/live/playlist.ts`; Classic's, which share the "clasic" community's room, likewise in `e2e/classic/`. Locally an already running server on 3100 is reused, so stop a leftover one after changing server code.
- **Helpers** (`e2e/helpers.ts`): import `test` and `expect` from there (its fixture runs axe in light and dark on every page visited); `logInAs(page, email)`, `api(…)`, `createSong(…)`; `openFromBar(page, name)` opens a page from the community bar's links or menus, `barPages(page)` lists them, `pickLayout(page, name)` picks a playlist layout; call `withoutPhoneLogin(page)` before opening the login page. The seed marks Classic hints seen for everyone but Eva.
- **Screenshots:** `npm run screenshots` builds and serves on port 3300 and writes `screenshots/<size>-<view>.png` (sorted by device), one test per view, each with its set of features switched on (the groups in `e2e/screenshots/views.ts`; each set's views in `e2e/screenshots/shots/`, which `take.spec.ts` takes in order); one view: `npm run screenshots -- -g musicians`. A first test checks that every picture the manual shows is taken.
- **Training videos:** `VIDEO_DB=<a real-data import> VIDEO_FILMER=<an owner's email in it> npm run videos` builds, serves a copy of that real import on port 3400 and writes `<name>.mp4` to `VIDEO_OUT` (default `~/norless-videos`), outside the repo, since they show real data; one video: `-- -g 2-building`. The tools in `e2e/videos/film.ts`: `film` (devices side by side), `say` (a caption), `press` (a ring, the mouse gliding or a fingertip, the click heard), `key`, `type`, and `lastService` / `lastServiceStart` for the real playlist. Needs ffmpeg.

## Which tests to run

- While working: `npm run check` (about 20 seconds) and the e2e files of the views touched.
- Before archiving a change: the full `npm run e2e`, and the screenshots of the views that changed.
- The dev servers (`run-dev.sh`, ports 3000 and 5173, and the converter on 3900; the e2e run's is on 3901) and `tailscale serve` don't get in the way of either.
